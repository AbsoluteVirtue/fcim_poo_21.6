# Особенности наследования в С++
## Включение (наследование реализации)
```C++
struct A {
   int x;
   void f() { x = 0; }
};

struct B : public A {

};
```
В случаях, когда одна структура (класс) наследует другую, они формируют отношение "надтипа" и "подтипа": в любом сценарии, где используется тип A, можно без потери информации использовать и тип B.
```C++
void test(A a) {
    a.f();
}

int main(void) {
    A a; test(a);   // call    "_ZN1A1fEv"
    B b; test(b);   // call    "_ZN1A1fEv"
}
```
В примере выше оба вызова функции `test` воспринимаются компилятором одинаково, потому что и для объекта `a`, и для объекта `b` будет вызван метод класса A, т.к. в отсутствие такого же метода в классе B, используется копия включенного в объект `b` анонимного объекта типа A--`b.A::f()`.

Даже если явно объявить в классе B метод f с аналогичноым заголовком, вызываться в этом случае он не будет.
```C++
struct A {
   int x;
   void f() { x = 0; }
};

struct B : public A {
   void f() { x = 1; }
};

void test(A a) {
    a.f();
}

int main(void) {
    A a; test(a);   // call    "_ZN1A1fEv"
    B b; test(b);   // call    "_ZN1A1fEv"
}
```
Это связано с тем, что функция `test` принимает объект типа A по значению, а значит при вызове с аргументом типа B значение аргумента автоматически компилятором приводится к типу A, и вся информация, присущая только объекту B, игнорируется.

Из этого есть важное следствие. Расширяя тот или иной класс и получая информацию из него (наследуя структуру и поведение), у объектов-потомков появляется возможность выступать в роли своих родительских типов, не повторяя или переписывая их код. Т.е. в любой ситуации сохраняется возможность вызова тех методов, которые определены на вершине всей иерархии.
## Расширение и переопределение
Для переопределения родительских методов--замены их кода на другой с помощью наследования--необходимо включить механизм динамической диспетчеризации. Это возможно посредством виртуальных таблиц.
```C++
struct A {
   int x;
   virtual void f() { x = 0; }
};
```
Для генерации виртуальной таблицы достаточно указать на виртуальный метод (либо--реже--виртуальную связь с предком) в одном из классов, метод которого планируется переопределять.

Здесь важно понимать, что функцию с параметром соответствующего типа надо изменить, чтобы аргумент передавался по ссылке.
```C++
void test(A& a) {
    a.f();
}
```
Это нужно для того, чтобы по этой ссылке можно было находить реальный код виртуального метода (т.е. переопределение метода в семействе методов, которое формируется с помощью наследования) в таблице указателей.

Т.о. в данной ситуации результатом будет то, что функция `test` становится обобщенной функцией с поздним связыванием, так как версия метода `f()`, от которого она зависит, будет подбираться с помощью адреса аргумента в момент вызова.
```C++
struct B : public A {
   void f() { x = 1; }
};

struct C : public A {};

int main(void) {
    A a; test(a);
    B b; test(b);
    C c; test(c);
}
```
Это позволяет сохранять отношение подтипов между классами в иерархии, но изменять реализацию зависимостей незаметно для клиента и независимо друг от друга.
## Интерфейсы
Иногда бывает необходимо разделить заголовки методов класса и их реализации. С одной стороны, это делает класс абстрактным (он больше не содержит информацию о поведении и структуре типа, а только хранит имена методов). С другой стороны, это позволяет делать клиенты этого класса полностью обобщенными, потому что они не зависят ни от одной конкретной реализации, а только от имен (интерфейса).

Для этого любой виртуальный метод в классе-родителе объявляется "чисто" виртуальным с помощью специального синтаксиса (явно обозначается отсутствие у него тела). Такой класс нельзя инстанциировать, потому что вызывать его методы запрещено. При этом, на такой класс можно ссылаться (например, в параметрах функции).
```C++
struct A {
   int x;
   virtual void f() = 0;
};

void test(A& a) {
    a.f();
}
```
При наследовании такого класса все потомки обязаны включать в свое определение переопределенные версии всех методов родительского абстрактного класса, чтобы компилятор не посчитал и их абстрактными (такие методы полезно помечать словом `override`).
```C++
struct B : public A {
   void f() override { x = 1; }
};

struct C : public A {
    void f() override { x = 2; }
};

int main(void) {
    B b; test(b);
    C c; test(c);
}
```
Нужная версия метода все также подбирается из виртуальной таблицы в момент передачи аргумента. При этом сам параметр не связан ни с какой реализацией, и даже при отсутствии конкретных классов функция, ссылающаяся на абстрактный класс остается правильной и всегда компилируется. 
## Альтернатива наследованию для создания слабых интерфейсов
Можно было братить внимание на то, что наследование не различает отношение подтипов, которое явно не задано как часть иерархии. Например, 
```C++
struct A {
   int x;
   void f() { x = 0; }
};

struct X {
    int x;
    void f() { x = 0; }
};

struct C {
	A a;
};
```
Из примера выше очевидно, что объекты A, C и X имеют одинаковую структуру и поведение. При этом, использовать их напрямую друг вместо друга не получится.

Язык позволяет сделать это через обобщенные функции (т.е. семейства функций), используя вместо абстрактных классов шаблоны.
```C++
template <class I> void test(I& i) {
    i.f();
}

int main(void) {
    A a; test(a);
    X x; test(x);
}
```
Шаблон сам описывает интерфейс, который функция пренимает, не определяя его явно (нигде не указано, что именно должно быть реализовано). В такой ситуации классы A и X не обязаны быть частью общей иерархии наследования. Достаточно того, что они оба реализуют метод `f()`. Т.е. с точки зрения клиента ситуация идентична случаю с использованием абстрактного класса. С точки зрения реализации здесь уже нет динамического выбора нужного метода, потому что шаблоны не генерируют виртуальную таблицу или ее аналоги. Вместо этого генерируется множество перегрузок функции `test`--для каждого из типов данных, которые используются в качестве аргументов. 

Шаблон в примере выше не релает проблемы с использованием класса C в качестве аргумента, потому что синтаксически нельзя обойти явное включение нужного объекта внутри при вызове функции. Эту ситуацию можно решить с помощью `type traits`.
